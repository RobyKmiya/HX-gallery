二、缺点：P0 数据安全与崩溃风险（四项均已在第一批修复，见 12.7）

P0 1. 迁移备份可能是不完整快照
src-tauri/src/db.rs:282-305 · backup_database()

let _ = conn.execute_batch("PRAGMA wal_checkpoint(TRUNCATE);") 忽略失败，随后 fs::copy(library.db, backup) 只复制主库。WAL 模式下，若 checkpoint 未成功（CLI 或另一实例正持有连接），最近写入仍在 -wal 里，备份静默缺数据。HANDOFF 明确"备份只允许复制元数据"，因此这个备份的可靠性很关键。

建议：改用 VACUUM INTO '备份路径' 或 rusqlite::backup::Backup 得到一致性快照；成功后校验文件大小/PRAGMA integrity_check，失败则中止迁移而非继续。
P0 2. 行解析错误被静默吞掉，画集会"凭空消失"
library.rs:801（主列表）、625 / 655 / 687 / 260（分组与扫描）、db.rs:1422 / 1467

多处使用 rows.filter_map(Result::ok).collect()。任何一行 row.get() 失败（NULL、类型不符、分组列错位）该画集就被悄悄丢弃，界面显示 total = 170 却只渲染 168 本，且没有任何错误提示。这是最难排查的一类问题。

建议：统一改成 collect::<Result<Vec<_>, _>>()?，让错误冒泡到命令层并 toast。
P0 3. 图片解码没有像素上限，存在 OOM / 进程退出风险
archive.rs:154-174、reader.rs:121-127 / 148-150 / 182-200、Cargo.toml:43 panic="abort"

只限制了压缩后字节数（封面 64 MB、页面 32 MB），image::load_from_memory 没有设置 Limits。一张高压缩比的"图片炸弹"（例如几 MB 的 30000×30000 PNG）解码时会申请 GB 级内存。叠加 release 的 panic = "abort"，分配失败或 panic 会直接终止整个桌面进程，无保存、无错误对话框。importer.rs:268 的 expect("temporary path missing") 也在导入路径上保留了 panic 可能。

建议：用 ImageReader::with_guessed_format().limits(Limits::default().max_alloc(Some(256MB)).max_image_width/height(...))；移除命令路径上的 expect/unwrap；评估把 panic="abort" 改回 unwind 并加顶层崩溃日志。
复核修订（严重度）：保留 P0 定性——panic="abort" + 无解码上限确实会让一次异常直接终止进程，事实无误。但执行顺序下调到 P0-1 / P0-2 之后：这是本地离线个人库、没有外部恶意输入通道，现实触发条件是「某张超大扫描图 / 损坏文件」而非刻意构造的图片炸弹；后果是崩溃后重启可恢复，而 P0-1（备份缺 WAL 数据）与 P0-2（行错误静默丢画集）是不可逆、且没有任何提示的数据丢失。第十二章 12.6 已据此把第 1 步拆成 1a（静默丢数据两项）→ 1b（崩溃与破图两项）。
P0 4. 封面缓存非原子写，坏文件会永久卡住
archive.rs:123-142 / 176-184

image.save(destination) 直接写最终文件；中途失败/断电留下截断的 JPEG，而下次判断是 if !cover_path.exists() —— 文件存在就再也不重生成，该画集长期显示破图。错误分支里的 remove_file 只覆盖显式报错，覆盖不到崩溃场景。

建议：写 .tmp → fs::rename 原子替换；读缓存时校验文件头/可解码；提供"重建封面"命令批量修复。

三、缺点：P1 正确性与明显卡顿（第 5 条为已确认设计决策、第 14 条复核降 P2）

已确认 · 非缺陷 5. 默认评分 60 —— 用户拍板保留的产品设定
db.rs:172 / 501、library.rs:418-435、ArchiveCard.tsx:103-106

初稿把「新画集自动评为 60、未评分筛选恒为空、分组全挤进 41–60」列为语义冲突。你已确认这是有意设计：下载入库的大多是喜欢的，默认即纳入及格线。因此 rating DEFAULT 60、insert_archive 写入 60 与卡片显示 60 分均保持不变，本批及后续批次都不改评分数据、不做迁移；「未评分」筛选恒为空是这一设定的预期结果，不再计为缺陷，也不再列入推进顺序。

保留前提下的可选项（非本批、非必须）：若将来想区分「默认 60」与「手动改过」，可加一个 rating_manual 布尔列，仅由 set_rating 置位，把该筛选改名为「未手动评分」——默认值与现有数据一律不动。若不需要这个区分，也可以直接从筛选 UI 移除恒为空的 bucket，避免用户点了没反应。两点都需你另行确认后再做。
P1 6. 阅读器整页图片走 base64 JSON，是翻页延迟的根因
reader.rs:133-137 / 158-162、lib.rs:857-922

data:{mime};base64,... 单页最大 32 MB 原始字节 → 约 43 MB 字符串，每翻一页都要「ZIP 解压 → Rust 序列化 JSON → IPC 传输 → WebView 解析 base64 → 图片解码」。M19 的"9–10 ms 换帧"靠预取缓存实现，冷启动首帧、跳页、未命中缓存的页仍受这条链路限制；高分辨率扫描图尤其明显。

建议：改为注册自定义 URI scheme（register_uri_scheme_protocol）直接返回字节流，或解压到缓存目录走 asset://，或至少用 tauri::ipc::Response 二进制通道；前端 <img src> 由浏览器自行流式解码与缓存。这是投入产出比最高的一项性能升级。
P1 7. 缩略图无缓存、每次都全解码原图
reader.rs:140-163（与 read_page_bytes 165-203）

每次 read_thumbnail 都重新打开 ZIP、load_from_memory 解码整页原图、再 thumbnail() 缩放并 JPEG 编码。缩略图侧栏 N 张就是 N 次原图全解码，且没有任何磁盘/内存缓存；每次翻页也重新 ZipArchive::new 解析中央目录。

建议：按 (content_hash, page_index, max_edge) 落盘缓存缩略图；提供 read_reader_thumbnails(archive_id, indices[]) 批量命令；缓存打开的 ZIP 句柄（LRU）。
P1 8. 全局页表缓存永不淘汰，且失效判定不严谨
reader.rs:28-31 / 33-42 / 70-101

static Mutex<HashMap<PathBuf, Manifest>> 每个打开过的压缩包都常驻内存（每页一个 String），切换库也不清理，长时间使用持续膨胀。缓存有效性只靠 (mtime_ms, len)：同一毫秒内替换同大小文件（复制覆盖很常见）不会失效，导致页码与内容错位。

建议：改 LRU + 容量上限，切换库时 clear()；stamp 增加 content_hash 或 Windows 文件 ID / 采样头尾字节。
P1 9. settings.json 静默失败 + 非原子写
lib.rs:87-110；参见 HANDOFF §6.3「UTF-8 无 BOM、双反斜杠」

serde_json::from_str(...).unwrap_or_default()：配置损坏（BOM、手写错、写入中断）时直接回到欢迎页且不给任何提示。fs::write 失败只 eprintln!，open_library 仍返回成功 —— 用户以为切换成功，下次启动却丢了库路径。这个坑已经在交接文档里被记录过，说明确实发生过。

建议：tmp + rename 原子写；读取失败时把错误写入 startup_error 让前端显示"配置损坏，已保留备份，请重新选择库"；写失败时让命令返回错误。
P1 10. 数据库迁移不是事务，失败会留半迁移库并反复堆积备份
db.rs:135-158 / 308-373 / 282-305

upgrade_schema 连续执行十余条 ALTER TABLE / UPDATE / CREATE INDEX / 回填，全程不在事务里，PRAGMA user_version 最后才写。中途失败 → 数据库处于半升级状态但版本号仍旧；下次启动重跑迁移，还会再生成一份带时间戳的备份（无保留策略，backups 目录无限增长）。

建议：整个迁移包进 conn.transaction()，失败自动回滚；按 version 记录迁移历史；备份只保留最近 N 份并做完整性校验。
P1 11. 导入不可取消、进度事件无任务隔离、异常会留残留
importer.rs:21-30 / 98-357 / 359、lib.rs:180-213

spawn_blocking 里没有取消标志，拖入几百个大文件只能等；app.emit("import-progress") 全局广播且不带任务 ID，若同时触发两次导入，进度与结果会互相覆盖；.gallery/tmp/<uuid>/*.part 只在正常结束时清理，崩溃/被杀后永久残留。

建议：加 AtomicBool 取消令牌 + 前端"取消导入"按钮；事件带 taskId；启动时清理超过 24h 的 tmp 目录；导入队列化，禁止并发导入。
P1 12. 导入与主连接并发写，可能触发 database is locked
importer.rs:48-63、db.rs:82、lib.rs:976-993

导入自己 db::open_library(root) 开了第二条连接，AppState 也常驻一条；导入逐条 insert_archive 自动提交，密集写入配合 busy_timeout = 5000 容易撞锁。同时所有查询被同一把 Mutex<AppInner> 串行化，query_archives 是同步命令、持锁跑完 3 条 SQL（分组 + COUNT + 分页），导入期间 UI 的筛选/翻页会明显排队。Tauri 同步命令默认在主线程执行，进一步放大阻塞感。

建议：导入用单事务分批提交（每 N 条）；查询命令改 async + spawn_blocking；把状态锁拆成 Arc<Mutex<Connection>> 或只读连接池；适当提高 busy_timeout 并对锁错误做重试。
P1 13. 批量标签逐个 IPC 往返，且中途失败留下半应用状态
DetailDrawer.tsx:328-356（HANDOFF §6.2 亦提及）

for (const name of names) { await api.addTag(card.id, name) } 串行调用；几十个标签尚可，几百个会逐条等待，且第 N 条失败时前面已写入、UI 只提示一条错误。同类问题还有 LibraryView.tsx:1138 批量删除（并发但无成功/失败明细）。

建议：后端加 add_tags_bulk / delete_archives_bulk 单事务命令，返回成功与失败明细；前端一次提交、失败可整体回滚。
P2 · 复核降级 14. 内容安全策略完全关闭 —— 纵深防御缺失，非当前漏洞
src-tauri/tauri.conf.json:24-29、capabilities/default.json:6-10

"csp": null 是为了放行阅读器的 data: 图片。当前代码没有 dangerouslySetInnerHTML（React 默认转义）、没有已知注入点，因此不构成 P1；复核意见成立，本条降为 P2 纵深防御，且不应与命令权限问题混在一节。真正该按 P1 处理的是第十章 B4：Tauri 2 自有命令不受 capability ACL 约束、open_library 只判空、import_paths 无白名单、library_id 未校验就拼路径 —— 这是不需要任何注入前提就成立的权限面问题。

建议：随第 3 步「阅读器数据通道重构」一并收口：改用自定义协议 / asset: 后可禁用 data:，再配置最小 CSP（default-src 'self'; img-src 'self' asset: data:; script-src 'self'）；asset scope 收紧到 $APPCACHE/covers/**；可评估 Isolation 模式。不与 B4 的 ACL 改造捆绑排期。

四、可升级点（架构与产品能力）

  • 阅读器数据通道重构（对应 P1-6）：自定义协议 / 二进制 IPC + 页级磁盘缓存，可同时解决翻页延迟、缩略图解码、内存占用与 CSP 四个问题，是最值得做的一次架构升级。
  • 结构化错误码：目前所有命令都是 Result<T, String>（lib.rs 全篇）。改用 thiserror 枚举 + serde 错误码，前端才能区分「文件缺失 / 数据库锁 / 参数非法 / 权限不足」并给出针对性恢复动作（重新定位文件、稍后重试、跳转设置）。
  • 搜索能力升级：library.rs:463-487 ≥3 字符走 FTS5 trigram 严格子串短语，1–2 字符走 %LIKE% 全表扫描。实测 trigram：搜「妄想秘話」可命中，但用户加空格写成「妄想 秘話」就搜不到；繁简、错字、同义词、拼音都无容错，且 1–2 字查询随库增大线性变慢。建议按空格拆词做 AND、加 LIKE 兜底、中文分词或拼音索引，并在无结果时给出原因提示。
  • 维护命令：db.rs:390-409 的 FTS 只在表不存在时 rebuild，缺 fts rebuild / integrity-check；也缺 PRAGMA optimize、WAL checkpoint、VACUUM 与"重建全部封面"等自助修复入口。可在 galleryctl 加 maintain 子命令族。
  • 单实例 + 窗口状态：HANDOFF §5.4 记录过多实例引发 WebView2 0x8007139F。加 tauri-plugin-single-instance，第二实例聚焦已有窗口并转发拖入路径；同时持久化窗口尺寸/位置（当前 tauri.conf.json 固定 1280×820）。
  • 发布链路：代码签名（避免 SmartScreen 警告）、tauri-plugin-updater 自动更新、MSI/便携版、校验和，HANDOFF §6.2 已列但未做。
  • 主题与个性化：App.css:2 固定 color-scheme: dark，没有浅色 / 跟随系统 / 主题切换；快捷键、自动翻页档位（5/8/12 秒）、每页尺寸等也不可配置。长时间看图的用户常需要浅色与自定义节奏。
  • 格式与元数据：当前只支持 ZIP/CBZ 与 8 种图片扩展名（archive.rs:29-39）。可评估 RAR/7z、AVIF/HEIC/JXL、以及从压缩包内 ComicInfo.xml 读取标题/作者/标签，减少手工录入。

五、可优化点（性能与代码结构）

  • 深分页与重复 COUNT：library.rs:334 / 692-698 / 751 每次查询都 COUNT(*) + LIMIT ? OFFSET ?。当前 170 本无感，上万本时深页与每次筛选都要全表扫描。建议按排序键做游标分页、缓存 total（筛选条件不变时复用）。
  • 首屏无代码分割：实测单个 379 KB JS + 69 KB CSS，14 个组件全部静态 import。阅读器、标签中心、回收站、标签导图都是"打开弹层才用"，建议 React.lazy + 动态 import 按界面拆包，冷启动更快。
  • 巨型文件：App.css 5016 行 / LibraryView.tsx 2833 行 / db.rs 2139 行 / TagCenter.tsx 1382 行。CSS 里 12 处 z-index 分散、只有 4 个 @media（720/860/1120），而窗口 minWidth = 980 —— 720/860 两个断点在桌面窗口里永远不会触发，属于死代码。建议按模块拆 CSS、抽自定义 hooks、用 design tokens 统一管理层级与颜色。
  • 静默忽略返回值过多：importer.rs 里十余处 let _ = fs::remove_file(...)、db.rs:288 的 checkpoint、lib.rs:514 的封面删除。清理失败会积累垃圾且无人知晓，建议至少汇总进导入报告 / 日志。
  • 版本号三处手工同步：package.json:4、Cargo.toml:3、tauri.conf.json:4 都是 1.0.0，发版容易漏改。建议单一来源 + 构建脚本校验。
  • 文档与实现不符：docs/AGENT_API.md:33 写「分页命令使用游标」，实际 search --page/--limit 是 OFFSET 分页，只有 tags list --after 才是游标。
  • 无运行日志：只有零散 eprintln!（lib.rs:56/63、db.rs:301），用户机器上出问题无法追溯。建议文件日志 + 轮转 + 「导出诊断信息」入口。

六、使用手感 / 交互改进点

  1. 命令 ACL（B4 的第 ① 项）——Tauri 2 中自有 #[tauri::command] 不受 capabilities 约束，自定义 permission 只对插件命令生效。要真正 ACL 化，得把 45 个命令拆进一个内部 plugin，是一次结构性改动，不宜和连接层混在一批。本批先做了「入口校验」（路径、library_id、cover_key、入参上限），把「可被任意脚本滥用」收窄成「可被任意脚本调用但参数受约束」。
  2. 整批导入的大事务——没有做。文件复制与哈希是 IO，若包在事务里会全程持有写锁，界面侧任何写操作都要等到导入结束；而每条 insert 本身已是单语句原子。真正需要原子性的「写库 + 收藏夹」这一组已经用事务包住了。
  3. FTS 出错回退 LIKE——搜索词已做控制字符清洗与限长，拼出的必然是合法的 FTS5 短语，命中非法输入导致报错的路径基本被堵死；完整的「查询失败后整条语句降级重试」需要在 query_archives 里做二次执行，留到第 3 步随阅读器通道一起改。
